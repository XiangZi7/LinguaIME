# LinguaIME：中英双语智能输入法开发规格说明

> **文档用途：** 产品需求、UI/UX 规范、技术架构、数据模型、开发任务与验收标准。  
> **目标平台：** Windows 10/11，优先验证 Windows 11。  
> **技术方向：** Windows TSF/COM + C++ 原生宿主 + Rust 输入引擎 + Tauri 2 + Vue 3 + TypeScript + Tailwind CSS v4 + SQLite。  
> **当前优先级：** 中文拼音输入 → 纵向中英双语候选窗 → 管理应用 → 英语辅助 → 日语等独立引擎。

---

## 0. 给开发 AI 的总指令

你正在开发 LinguaIME。请严格遵循本文件。它不是普通网页、聊天机器人，也不是只有设置页面的 Tauri 应用。

**最高优先级：候选窗口是产品核心，管理应用是辅助工具。** 候选窗口必须能在记事本、浏览器、IDE、聊天软件等 Windows 应用中工作。不能要求用户先打开 Tauri WebView；不能让网络请求或英语释义拖慢基本输入。

### 开发顺序

1. 验证 TSF/COM 最小输入原型。
2. 建立原生宿主与 Rust 输入核心之间的稳定接口。
3. 实现中文拼音组合、候选生成、选择和提交。
4. 实现纵向候选窗：中文主词条、英文释义、词性、页码。
5. 实现翻页、焦点管理、光标定位、高 DPI 和多显示器。
6. 实现 Tauri 管理应用和输入设置。
7. 接入本地词典、个人词条、用户词频和 SQLite。
8. 增加用户主动触发的英语学习和整句翻译。
9. 完成安装、卸载、日志、隐私、性能与兼容性测试。
10. 在基础架构稳定后再接入日语引擎。

### 禁止事项

- 不用 WebView 替代 Windows TSF 输入法接入。
- 不把候选窗口依赖在管理应用主窗口上。
- 不在每次按键时调用在线翻译。
- 不把任意中文候选逐字翻译后当作可信释义。
- 不虚构词性、释义、例句、音标或发音状态。
- 不默认上传用户输入的完整文本。
- 不在普通文本状态下无条件拦截 `-` 和 `=`。
- 不把规划中的日语能力显示成已经可用。
- 不把所有业务写进一个巨大组件或模块。
- 不只画静态图，必须实现真实状态、交互和测试。

# 1. 产品定位与范围

## 1.1 产品定位

LinguaIME 是一款以中文拼音输入为起点、强调中英双语直观呈现和多语言扩展能力的 Windows 输入法。传统输入法主要展示中文候选，LinguaIME 则在有可靠词典数据时，直接在候选旁显示常见英文单词或短语。

详细释义、例句、发音、收藏和整句翻译属于可选学习能力，默认不打断输入。

用户输入：

```text
wo'shi'shuo
```

候选窗可以呈现类似结构：

```text
wo'shi'shuo
1  我是说      I mean
2  我是        I am
3  卧室        bedroom
4  我试        I try
5  沃什        Wash
                         1/27
```

以上仅为布局示例。正式词条和释义必须来自词典或经过校验的数据，不得直接作为真实词库。

## 1.2 核心原则

1. **输入优先**：基础中文输入不能被学习功能打断。
2. **双语直显**：在数据可靠时显示简短英文释义。
3. **渐进披露**：默认短信息，详细信息按需展开。
4. **本地优先**：拼音解析、候选排序和用户词频优先本地处理。
5. **独立语言引擎**：中文、日语等各自使用合适的解析算法。
6. **隐私透明**：清楚区分本地功能和联网功能。
7. **Windows 原生体验**：候选窗不是普通网页卡片。
8. **渐进交付**：先稳定输入，再增加智能辅助。

## 1.3 MVP 必须包含

- 可验证的 Windows TSF 接入。
- 中文全拼组合输入、候选生成、数字选择、提交与取消。
- 纵向候选窗口与候选分页。
- 双语简洁模式：中文候选 + 英文短语/释义 + 可选词性。
- 纯中文、双语简洁、双语详细三种显示模式。
- 中英文标点与基础输入设置。
- 本地词典读取。
- 基础个人词条或用户词频学习。
- Tauri 管理应用的基础设置页。
- 安装、退出、日志和错误处理。
- 在记事本、浏览器文本框和至少一个常见编辑器中验证。

## 1.4 后续功能

- 英语详细学习面板、收藏、生词本。
- 用户主动触发的整句翻译。
- 发音、例句和常见搭配。
- 词库导入导出、学习统计。
- 日语罗马音输入。
- 其他语言引擎与更高级的上下文排序。

# 2. 系统架构

## 2.1 逻辑架构

```text
Windows Apps (Notepad / Browser / IDE / Chat)
                  │
                  ▼
       Native TSF / COM Host (C++)
       composition · key routing · focus
       candidate window · text commit
                  │
                  ▼
             Rust Input Core
  ┌─────────────────────────────────────┐
  │ input-engine-api                    │
  │ pinyin-engine                       │
  │ candidate-ranking                   │
  │ dictionary / bilingual-lexicon      │
  │ user-learning / storage             │
  │ english-learning                    │
  │ engines/japanese (future)           │
  └─────────────────────────────────────┘
                  ▲
                  │ commands / IPC
                  ▼
       Tauri 2 Management Application
       Vue 3 · TypeScript · Tailwind v4
       settings · dictionary · learning
       appearance · privacy · shortcuts
```

此图描述逻辑边界，不代表已确认的进程模型。COM 激活方式、线程模型、候选窗口技术、FFI 方式和部署方式必须在技术验证阶段确定。

## 2.2 模块职责

### Native TSF Host（C++）

- 实现并注册所需的 Windows TSF/COM 接口。
- 接收键盘事件，决定由输入法处理还是交还目标应用。
- 管理组合文本、光标和文本提交。
- 管理候选窗显示、隐藏、定位与焦点行为。
- 处理切换应用、焦点变化、取消组合和卸载。
- 调用 Rust 核心获取候选结果。
- 不实现整个拼音词典，不执行在线翻译。

### Rust Input Core

- 统一输入引擎 API。
- 中文拼音解析与候选生成。
- 词典检索、排序、分页。
- 用户词频和个人词条。
- 双语释义查询。
- 本地数据访问。
- 英语学习服务抽象。
- 未来语言引擎管理。

### Candidate Window

- 展示组合串、候选、序号、选中态、页码和快捷键提示。
- 展示中文主词条、英文短释义和词性。
- 支持三种显示模式。
- 需要时显示学习详情。
- 处理 DPI、屏幕边缘、多显示器和窗口定位。
- 尽量不抢目标应用焦点。

候选窗口渲染技术需比较 Win32 原生 UI 与其他合适方案的焦点、定位、可访问性、延迟和部署成本。不得默认要求 Tauri WebView 常驻输入关键路径。

### Tauri 管理应用

负责输入设置、语言与引擎、词库、英语学习、学习统计、快捷键、外观、隐私、诊断和更新。关闭管理应用不能让输入法失效。

# 3. 技术选型与边界

## 3.1 建议技术栈

| 层 | 技术 | 责任 |
|---|---|---|
| Windows 集成 | C++20、Windows SDK、TSF/COM | 原生输入法 |
| 输入核心 | Rust stable | 解析、候选、词典、学习 |
| 桌面管理应用 | Tauri 2 | 设置与系统集成 |
| 前端 | Vue 3、`<script setup lang="ts">` | 管理界面 |
| 样式 | Tailwind CSS v4 | 布局和主题 |
| 状态管理 | Pinia（按需） | 管理应用跨页状态 |
| 路由 | Vue Router | 管理页面 |
| 国际化 | vue-i18n | 管理应用多语言 |
| 数据库 | SQLite | 用户配置、词频和学习数据 |
| 构建 | CMake、Cargo、pnpm | 原生、Rust、前端 |

项目初始化时选取兼容版本并锁定依赖，不要让每次构建自动漂移版本。

## 3.2 FFI/API 要求

先定义稳定的数据契约，再决定 C ABI、`cxx` 或进程间通信。要求：

- 明确 API 版本和字符编码。
- 不跨边界直接传递复杂 Rust 所有权对象。
- 明确内存分配与释放责任。
- 错误使用结构化错误码。
- C++ 异常和 Rust panic 不得越过 FFI 边界。
- 输入关键路径不能等待网络。
- 异步结果应可取消或通过请求序号丢弃过期响应。
- 为数据结构保留 schema/version 字段。

逻辑类型草案：

```rust
pub struct EngineRequest {
    pub language: String,
    pub composition: String,
    pub cursor: usize,
    pub page: usize,
    pub page_size: usize,
    pub mode: CandidateDisplayMode,
}

pub struct Candidate {
    pub id: String,
    pub text: String,
    pub reading: Option<String>,
    pub translation: Option<String>,
    pub part_of_speech: Option<String>,
    pub short_gloss: Option<String>,
    pub source: CandidateSource,
    pub score: f64,
}

pub struct CandidatePage {
    pub composition: String,
    pub items: Vec<Candidate>,
    pub page_index: usize,
    pub page_count: usize,
    pub selected_index: usize,
    pub has_previous: bool,
    pub has_next: bool,
}
```

这些类型是逻辑模型，不代表 Rust 结构体可直接跨 FFI 安全传递。必须定义 C 兼容结构或明确的序列化协议。

# 4. UI 设计系统

## 4.1 核心视觉方向

保留参考图的布局逻辑：

- 白色紧凑悬浮窗。
- 顶部显示拼音组合串。
- 纵向排列候选。
- 左侧序号。
- 中文主词条。
- 右侧英文词或短语。
- 词性和短释义按需展示。
- 底部显示页码和键盘提示。
- 当前行用柔和浅绿色高亮，可提供蓝色主题选项。

升级目标是更现代、更清晰、更稳定，不要把原本高效的输入法变成大卡片、聊天面板或营销页面。

### 信息层级

1. 中文候选（最重要）。
2. 英文短语或词义。
3. 词性和简短说明。
4. 拼音组合串。
5. 页码与快捷键提示。
6. 详细学习信息（仅主动打开时）。

## 4.3 尺寸建议

这些数值为 UI 原型起点，不是最终物理像素规格：

- 默认宽度约 280–360 逻辑像素。
- 最小宽度约 240，最大宽度约 440。
- 组合串区域高约 30–38。
- 简洁候选行高约 30–38。
- 详细候选行高约 42–58。
- 内边距约 10–14。
- 候选项间距约 2–4。
- 圆角约 10–14。
- 默认展示 7–9 个候选。
- 页脚约 24–30 高。
- 使用细边框和柔和短阴影，不用夸张长阴影。

Windows DPI scaling、逻辑坐标与物理坐标必须分开处理，不能直接把 CSS 像素当成物理像素。

## 4.4 字体建议

- 优先使用系统可用的 Segoe UI Variable 和清晰的系统中文字体。
- 中文候选约 16–18 px。
- 英文释义约 12–14 px。
- 词性和短释义约 10–12 px。
- 拼音约 12–13 px。
- 序号、页码和快捷键提示约 10–12 px。

测试中文、英文、日文混排、字体 fallback、基线对齐和不同 DPI，不依赖用户一定安装第三方字体。

# 5. 候选窗口规格

## 5.1 标准布局示意

```text
┌──────────────────────────────────┐
│ wo'shi'shuo                      │
├──────────────────────────────────┤
│ 1  我是说        I mean           │
│    phr. · 我的意思是              │
│                                  │
│ 2  我是          I am             │
│                                  │
│ 3  卧室          bedroom          │
│    n. · 房间、卧室                │
│                                  │
│ 4  我试          I try            │
├──────────────────────────────────┤
│ ↑↓ 选择  Enter 确认       1/27   │
└──────────────────────────────────┘
```

此为结构图。默认简洁模式不应强制每一行都出现第二行说明。

## 5.2 区域定义

### A. 组合串头部

- 显示当前拼音组合串。
- 可选显示输入模式，但默认不突出。
- 不显示宣传文案或大 Logo。
- 组合串过长时采用合理截断或滚动策略。
- 输入更新后及时刷新候选。

### B. 候选列表

每行包含：

- 序号。
- 中文候选主词条。
- 英文词或短语（可选）。
- 词性（可选）。
- 中文短释义（可选）。
- 学习标记（可选，默认关闭）。

逻辑组件：

```text
CandidateWindow
├── CompositionHeader
├── CandidateList
│   └── CandidateRow
│       ├── CandidateIndex
│       ├── CandidateMainText
│       ├── CandidateTranslation
│       └── CandidateMetadata
└── CandidateFooter
```

若最终使用原生 C++ UI，这只是职责划分，不强制使用 DOM。

### C. 页脚

- 显示当前页/总页数，例如 `1/27`。
- 提示必要的快捷键。
- 候选很少或空间不足时隐藏次要提示。
- 页脚视觉权重低于候选内容。

## 5.3 候选行两种排版

### 单行优先（双语简洁模式）

```text
1  我是说       I mean
2  卧室         bedroom
3  我试         I try
```

### 必要时双行（双语详细模式）

```text
1  我是说       I mean
   phr. · 我的意思是
```

规则：

- 只有有价值的数据才展示第二行。
- 不为缺失信息预留大块空白。
- 行高应稳定，避免打字时窗口反复跳动。
- 详细模式可使用双行，简洁模式优先单行。

## 5.4 选中态

- 选中背景覆盖整行。
- 中文、英文、词性和序号均保持可读。
- 状态切换不能导致布局位移。
- 键盘选中状态与引擎选中索引一致。
- 鼠标悬停不能意外覆盖键盘选择。
- 默认浅绿高亮，可选浅蓝高亮。
- 行间距、圆角和高亮范围一致。

## 5.5 释义规则

展示优先级：

1. 常见英文单词或短语。
2. 词性。
3. 一条简短中文释义。
4. 例句、发音等详细内容。

数据缺失时隐藏字段，不显示伪造占位词。在线结果应异步补充，不能阻塞候选选择。短语优先使用完整表达，例如“我是说 → I mean”，而非逐字翻译。

## 5.6 长内容与自适应

- 长英文截断，完整内容可在详情中查看。
- 单个词条不能撑破最大宽度。
- 常见词性可使用 `n.`、`v.`、`adj.`、`adv.`、`phr.`。
- 未知词性不显示空标签。
- 多义词默认显示一条最常用且可信的释义。
- 候选数量少时自适应高度；超过最大高度时分页或滚动。
- 翻页不应导致窗口位置突然跳动。

# 6. 键盘、鼠标与窗口行为

## 6.1 输入生命周期

```text
Idle
  └─ 输入拼音 → Composing
       ├─ 更新组合串
       ├─ 生成候选
       ├─ 上下选择 / 翻页
       ├─ 确认候选 → Commit → Idle
       └─ Esc / 焦点变化 → Cancel 或按策略结束
```

必须区分组合串、候选列表、选中项和已提交文本，避免每次按键就提前提交导致退格和候选选择失效。

## 6.2 按键表

| 按键 | 建议行为 | 约束 |
|---|---|---|
| 字母键 | 更新拼音 | 仅输入法激活时处理 |
| Backspace | 删除组合串末尾字符 | 空串时按明确策略结束组合 |
| 数字 1–9 | 选择对应候选 | 仅候选激活时拦截 |
| Space | 选择默认候选或依设置处理 | 不影响普通文本 |
| Enter | 确认当前候选或按配置处理 | 组合态规则明确 |
| Up/Down | 选择前后候选 | 边界行为一致 |
| `-` | 上一页候选 | 仅组合态/候选态 |
| `=` | 下一页候选 | 仅组合态/候选态 |
| Esc | 关闭候选或取消组合 | 不意外提交 |
| Ctrl/Alt/Win 组合键 | 默认交给系统/目标应用 | 除明确绑定外不拦截 |

### `-` 和 `=` 特别规则

- 只在组合串或候选列表激活时翻页。
- 普通文本状态必须原样传递。
- 输入 URL、代码、数学表达式和文件名时不得误拦截。
- 支持自定义、冲突检查和恢复默认。
- 自定义翻页键后应覆盖默认配置。

## 6.3 鼠标行为

- 单击候选行可选择或提交，必须统一定义行为。
- 悬停只提供视觉反馈，不自动提交。
- 学习详情入口不能占据主候选词点击区域。
- 点击外部时按明确策略隐藏或取消候选。
- 不抢夺目标应用焦点。
- 候选窗口应尽量不激活；需通过原生窗口实测验证。

## 6.4 窗口定位

- 优先显示在目标应用插入光标附近。
- 不遮挡关键输入内容。
- 靠近屏幕边缘时自动调整。
- 支持多显示器和不同缩放比例。
- 无法获得可靠光标位置时采用明确 fallback。
- 不能混用物理坐标与逻辑坐标。
- 切换窗口、焦点或显示器后及时隐藏或重新定位。

# 7. 三种显示模式

## 7.1 纯中文模式

显示组合串、中文候选、序号、页码和必要快捷键。隐藏英文释义、词性、学习标记和详细信息。

## 7.2 双语简洁模式（默认）

显示组合串、中文候选、可信英文短语/释义、必要词性和页码。

- 中文为主，英文为辅。
- 英文用低饱和强调色。
- 释义尽量单行。
- 不自动展示例句。
- 不自动播放发音。
- 不等待网络请求。

## 7.3 双语详细模式

可显示中文、英文短语、词性、短释义，以及用户主动打开后的音标、发音、例句、常见搭配、收藏和来源信息。

详细模式不能变成默认的大型面板，必须可快速切换。

# 8. 英语辅助与学习面板

## 8.1 触发原则

- 不因每次按键自动弹出。
- 通过快捷键、候选详情操作或管理应用主动打开。
- 在线翻译仅在用户明确触发后执行。
- 本地缓存优先。
- 失败不影响输入。
- 结果过期时取消或忽略。

- 支持复制译文。
- 网络失败时给出可理解的错误提示。

# 9. 多语言引擎设计

## 9.1 统一能力契约

每种语言引擎应提供：

- 语言标识、引擎版本、能力列表。
- 输入模式。
- 组合串更新。
- 候选生成和选择。
- 确认、取消。
- 词条详情查询。
- 词典版本和错误状态。

候选 UI、主题、设置、存储和学习管理可共享，但解析算法必须按语言独立。

## 9.2 中文拼音引擎

首期：

- 全拼组合串解析。
- 大小写与输入字符归一化。
- 词典前缀检索。
- 多音节词匹配。
- 候选生成、去重和词频排序。
- 用户词频学习。
- 候选分页。
- 自定义词条。
- 中英释义关联。

后续可扩展双拼、模糊音、简繁转换、上下文排序和更高级语言模型。

## 9.3 日语引擎（后续）

规划：

- 罗马音转假名。
- 假名转汉字候选。
- 日语词典、词性与读音。
- 活用/形态处理。
- 日语标点规则。
- 候选学习信息。

日语必须使用独立引擎，不可将中文拼音解析器伪装成日语输入。可研究 Mozc 等项目，但必须逐项审查源码、词典、模型与第三方组件许可证。

## 9.4 新增语言的必需工作

1. 语言元数据。
2. 独立输入引擎。
3. 候选生成器。
4. 对应词典与授权。
5. 键盘行为和输入规则。
6. 候选字段映射。
7. 自动化测试。
8. 发布与许可审查。

# 10. 双语词典与数据模型

## 10.1 设计原则

中文词条和英文释义可能是一对多、多对一且依赖语境。不要只把中文文本当作唯一翻译键。

示例：

- “我是说” → `I mean`
- “卧室” → `bedroom`
- “我试试” → `I'll give it a try` / `Let me try`（依语境）
- “苹果” → `apple`，但可能指品牌或专有名词。

首期可使用人工校验的短语映射和常见词典数据，之后再扩展上下文能力。

## 10.2 候选字段示例

```json
{
  "id": "candidate-unique-id",
  "text": "我是说",
  "reading": "wo shi shuo",
  "translation": "I mean",
  "part_of_speech": "phr.",
  "short_gloss": "我的意思是",
  "source": "offline_dictionary",
  "language": "zh-CN"
}
```

字段含义：

- `id`：稳定标识。
- `text`：提交到目标应用的文本。
- `reading`：读音或输入映射。
- `translation`：简短英文表达。
- `part_of_speech`：词性，可空。
- `short_gloss`：短释义，可空。
- `source`：数据来源。
- `language`：语言标识。

如果需要置信度，必须有可解释的评分来源，不能所有条目都硬编码成高置信度。

## 10.3 词条关系

建议区分：

- 输入词条：拼音与中文文本。
- 词典条目：标准词条、读音、词性、频率。
- 双语释义：源词条到目标语言表达的关系。
- 例句：学习数据。
- 用户词条：用户添加或由明确学习机制产生。
- 用户词频：本地选择统计。

一条中文词条可以关联多个英文释义，每条释义有来源、排序和适用场景。

## 10.4 词典授权

- 检查公开词典、词库和语料的许可证。
- 记录词典来源、版本、许可证和更新日期。
- 不打包版权不明的词库。
- 系统词典与用户自建词库分开管理。
- 导入前校验格式、重复项和数据完整性。

# 14. 输入引擎逻辑

## 14.1 拼音处理流程

1. 接收组合串。
2. 进行大小写与字符归一化。
3. 识别合法拼音片段。
4. 查询词典前缀和匹配项。
5. 根据分词路径生成候选。
6. 合并重复候选。
7. 应用词频、用户偏好与可用上下文排序。
8. 返回候选与分页元数据。

第一阶段不应承诺完整神经语言模型或超大规模上下文预测。

## 14.2 候选排序

建议从可解释的基础评分开始：

```text
final_score =
    dictionary_frequency_weight * frequency_score
  + user_preference_weight * user_score
  + phrase_match_weight * phrase_score
  + context_weight * context_score
  + recency_weight * recency_score
```

权重通过测试数据和反馈调优。不能只因为候选有英文释义就无条件提升中文候选排名。

## 14.3 分页与异步请求

- 引擎页码和 UI 展示页码必须统一映射。
- 翻页后有明确选中项规则。
- 空列表隐藏或禁用翻页。
- 词典异步刷新时丢弃旧组合串结果。
- 每次查询使用请求序号或组合串版本。
- 本地查询应快速完成。
- 在线释义不能进入输入关键路径。
- 候选先展示可靠本地结果，再按需补充学习信息。
- 新信息到达时尽量稳定布局，避免窗口跳动。

# 15. 隐私、安全与可靠性

## 15.1 默认隐私行为

- 不默认记录用户在任意应用输入的完整文本。
- 用户词频只保存必要的词条标识和统计。
- 避免学习密码框、敏感字段和不应记录的内容。
- 整句翻译由用户主动触发。
- 联网前说明将发送的文本与服务提供商。
- 用户可关闭在线服务。
- 用户可以清空本地词频和学习记录。
- API Key 不进入源码、日志或默认明文配置。
- 日志不得包含完整输入、翻译原文或密钥。

## 15.2 崩溃恢复

- 输入核心崩溃不能让目标应用失去正常输入能力。
- FFI 边界有错误恢复策略。
- 数据库不可用时提供有限降级。
- 词典损坏不能造成宿主持续崩溃。
- 升级前备份或迁移用户数据。
- 日志记录错误码和必要上下文，不记录敏感文本。

## 15.3 安装与卸载

- 明确 TSF 注册、安装、卸载、更新和权限需求。
- 安装失败给出可操作错误。
- 卸载时让用户明确选择是否保留用户词典与学习数据。
- 发布前验证签名、安装包、升级与回滚流程。

## 16.1 Rust 单元测试

- 拼音归一化。

# 20. 必须在早期验证的技术风险

1. **TSF 宿主模型**：确认 COM 类、线程模型、激活和卸载方式。
2. **候选窗口技术**：比较原生 UI 与其他方案的焦点、定位、延迟、可访问性和部署复杂度。
3. **Rust/C++ 通信**：通过原型测量调用开销、线程安全、错误隔离和部署成本。
4. **词典数据**：确认来源、许可、检索性能、体量和更新机制。
5. **双语映射**：区分离线词典和用户主动请求的在线服务。
6. **学习隐私**：明确学习开关、敏感输入排除与清除机制。
7. **安装与签名**：验证 TSF 注册、位数、安装权限和升级流程。
8. **兼容性**：测试常见编辑器、浏览器、焦点变化和无障碍行为。

不要在未验证 TSF 与窗口行为之前，就先投入完整 UI 开发并假设它一定像普通桌面窗口一样工作。

# 22. 最终产品方向

LinguaIME 的差异化不在于“又一个带 AI 的输入法”，而在于：

- **纵向候选列表**：延续熟悉的输入法操作方式。
- **中文为主、英文直显**：在有可信数据时，每一行直接展示常用英文表达。
- **学习不打扰输入**：默认短释义，详情主动打开。
- **原生 Windows 体验**：轻量、快速、稳定。
- **多语言独立引擎**：先中文，后续扩展日语和其他语言。
- **本地优先与隐私透明**：基础输入不依赖网络，联网翻译清晰告知用户。

最终目标：用户输入中文时像使用熟悉的输入法一样高效，同时能自然看到有价值的英文表达；需要学习或翻译时，再进入更完整的辅助功能。
